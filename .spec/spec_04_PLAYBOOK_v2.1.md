# Blender × Godot MCP 遊戲 Pipeline — 箱庭版 Playbook v2.1

> v2.1 · 2026-10-26 · 給 coding agent 從空資料夾重跑
> 本檔只描述**工作目標與驗收方式**。所有實作細節（程式、設定檔、規格數值、座標、參數、工具設計、驗收門檻）都由執行的 model 自行推論與決定。

## 給人看的：怎麼開始

1. 建一個空資料夾，把本檔放到 `.spec/PLAYBOOK_v2.1.md`（資料夾裡不要放其他版本的 playbook 或前一次的成品）
2. 在該資料夾執行 agent，輸入：`讀 .spec/PLAYBOOK_v2.1.md，從頭執行。遇到 STOP 就停下來等我。`
3. 中斷或重啟後輸入：`讀 .spec/PLAYBOOK_v2.1.md 和 pipeline/progress.md，從未完成的步驟繼續。`

需要人手動做的事：安裝軟體（Phase 0）、agent 權限被擋時手動處理、在 Blender 裡啟動 MCP server 並重啟 agent（Phase 2）。

## 要做什麼

一個 3D 箱庭小遊戲「Coin Run」：玩家操作一台單輪小機器人，在浮空的箱庭地塊上收集 3 枚金幣，收齊後碰到終點旗就勝利。

- 所有 3D 模型（含地面）都由 Blender MCP 產生；Godot MCP 負責組裝與執行
- 模型不符合規格時，要能自動發現並回到 Blender 修正

### 使用者需求（已定案，執行時不要再問）

| 項目 | 需求 |
|---|---|
| 地圖 | 40×40 m 的可活動區域，四周有磚瓦牆，角色走不出去；地塊浮在天空中 |
| 風格 | 箱庭（桌上模型）風格，構圖豐富、畫面不單調；低模、平塗顏色 |
| 角色 | 小機器人，單輪；輪子要有轉動動畫，動畫在 Blender 製作 |
| 場景元素 | 樹、草叢、石頭、磚瓦牆、房子、古代奇幻風格建築、木箱、木桶 |
| 木箱 | 造型要和場景風格搭配，擺放位置要合理 |
| 地面 | 不能單調、看起來不能假：要有草坪、道路等；地面稍微有高低起伏 |
| 鏡頭 | 等角 45° 平滑跟隨；方向鍵相對鏡頭方向移動 |
| 按鍵 | 加速：鍵盤 A / 手把 X（按住）；煞車：鍵盤 B / 手把 B（按住）；跳躍：Space / Enter / 手把 A |
| 移動 | 一般行走速度 4 m/s；移動要靠力向量與摩擦力，有慣性 |
| 物理互動 | 加速時機身傾斜；木桶可以推動；撞到樹會搖晃並掉落葉；穿過草叢時草叢會晃 |
| 氣氛 | 陽光與陰影（暖色、柔和陰影、環境光遮蔽）；雲在空中漂移；樹和草叢隨微風擺動；移軸景深（迷你模型感） |

### 完成定義（DoD）

- [ ] 每個 3D 資產都通過自動規格檢查（Blender 端與 Godot 匯入後都符合規格）
- [ ] 自動 bot 測試通過：bot 從起點依序收集 3 枚金幣並抵達終點，輸出能判讀的進度與勝利訊息，且沒有腳本錯誤
- [ ] 自動物理測試通過：「移動」與「物理互動」兩列需求的每一項都有可量測的檢查
- [ ] 透過 Godot MCP 實際執行遊戲沒有錯誤；遊戲畫面截圖依附錄 B 檢查過
- [ ] 完成一次迴圈演練（Phase 9）
- [ ] `pipeline/REPORT.md` 已寫

## 工作原則

1. **資產規格檔是唯一真相**：每個資產都要先寫好規格（外觀描述、目標尺寸、面數上限、是否需要碰撞、需要哪些動畫），建模與檢查都以它為準。規格格式由你設計。
2. **自動檢查迴圈**：每次從 Blender 匯出後，都要匯入 Godot 並和規格自動比對。尺寸在 Blender 端與 Godot 匯入後都要在規格的 ±10%（至少 2 cm）內；另外檢查原點、面數、碰撞、動畫。不通過時要給出具體的修正建議，並分辨是建模問題還是 pipeline 問題。
3. **FAIL 處理**：記進 log（時間、資產、第幾次、檢查結果、判斷、對 Blender 的修正請求、結果）→ 回 Blender 修。同一資產每輪最多 3 次，超過就停下來問使用者。
4. **不要手動修改匯出的模型檔或 Godot 的匯入設定檔**；要改就回 Blender 重新匯出。
5. **工具優先順序**：建模用 Blender MCP；Godot 端優先用 Godot MCP，做不到時改用其他方式，並把原因記進 log 的「MCP 問題」。
6. **進度與紀錄**：
   - `pipeline/progress.md`：本檔各 Phase 的步驟清單，完成就打勾（`[v]` 通過、`[x]` 做了沒過、`[ ]` 未做），重啟後靠它續跑
   - `pipeline/log.md`：設計決策、每次檢查與修正、MCP 問題
   - 每個 Phase 完成後 `git commit`
7. **由你決定的事**：所有數值、座標、程式、設定檔、工具設計、測試門檻都由你推論。重要的決策在 log 的「設計決策」段落寫一兩行理由。
8. **衝突時的優先順序**：DoD > 使用者需求 > 其他美術判斷。
9. 看到 **STOP**：清楚告訴使用者要做什麼，結束這一輪等回覆。除了 STOP 和超過修正次數，不要停下來問。

## Phase 0：環境檢查（人工安裝，agent 只檢查）

1. 確認已安裝：Godot ≥ 4.3、Blender、Node.js ≥ 18、uv、git，並找到 Godot 執行檔的位置（找不到就問使用者）
2. 任一項缺少 → **STOP**，列出缺什麼、去哪裡下載

## Phase 1：專案骨架

1. 規劃專案結構：資產規格、pipeline 紀錄、自動化工具、Blender 原始檔、Godot 專案要分開放
2. 寫一份專案規則檔給 agent 讀（`CLAUDE.md`，並另存相同內容的 `AGENTS.md`），至少涵蓋：
   - 單位與座標約定（規格以哪個軟體的軸向為準、兩邊如何換算、角色正面朝向）
   - Blender 建模與匯出規則（每個資產怎麼組織、原點、材質限制、碰撞怎麼標示、`execute_blender_code` 每次只做一小步、不刪專案外檔案、不下載外部資產）
   - 每次匯出後必做的檢查，以及 FAIL 迴圈規則
   - Godot 端的檔案位置、輸入規則（只用使用者定案的按鍵）、MCP 使用規則
3. 設定 MCP 伺服器（Godot MCP、Blender MCP）與 agent 權限：Godot 工具與你的檢查工具可以自動允許；Blender 的程式執行工具**不要**自動允許。用 agent-switch + opencode 的話，參考 `.spec/PLAYBOOK_BLENDER_GODOT_MCP_SETUP.md`
4. 建立 Godot 專案與使用者定案的按鍵設定，並用程式確認按鍵真的有綁上
5. 建立自動化工具（實作方式自訂），至少要能：檢查環境（含 Blender MCP 埠能否連線）、讓 Godot 匯入資產、依工作原則第 2 點比對資產規格、跑 bot 測試、跑物理測試
6. 建立 `pipeline/progress.md`、`pipeline/log.md`，`git init`，做第一次 Godot 匯入，`git commit`

## Phase 2：連線 MCP（**STOP**，需要人工）

告訴使用者：
1. 在 Blender 安裝並啟用 Blender MCP addon，從 Blender 裡啟動 MCP server（不要開外部資產庫與生成器）
2. Blender 5.x 若有內建的 Blender Lab「MCP」擴充，先停用，否則會佔用同一個埠
3. 退出 agent 再重新啟動，核准 MCP 伺服器
4. 輸入：`讀 .spec/PLAYBOOK_v2.1.md 和 pipeline/progress.md，繼續`

重啟後由 agent 驗證：環境檢查通過，且 Godot MCP 與 Blender MCP 各成功呼叫一個唯讀工具。任一項失敗 → **STOP**，回報是哪一項。

## Phase 3：冒煙測試

挑一個最簡單的資產，完整走一次：寫規格 → Blender 建模 → 自檢外觀 → 匯出 → Godot 匯入 → 規格檢查 PASS → 放進一個測試場景 → 用 Godot MCP 執行沒有錯誤。打通後 `git commit`。

## Phase 4：資產

依附錄 A 為每個資產寫規格並建模，每個都走完自檢與自動檢查迴圈。先做角色與道具，再做建築；地面另外在 Phase 5 做。每類做完 `git commit`。

## Phase 5：地面

依附錄 C 建立整個箱庭地塊（也是 Blender 資產，同樣要通過規格檢查）。其他物件要能正確放在起伏的地面上。`git commit`。

## Phase 6：世界組裝

依附錄 D 在 Godot 組出整個箱庭：地面、外牆、所有場景元素、金幣、終點。版面要可以重現；之後要調整版面時，不需要逐一手動搬動上百個物件。`git commit`。

## Phase 7：遊戲邏輯、物理與氣氛

實作玩法（收集、勝利）、角色操控與移動、物理互動、鏡頭、氣氛效果，全部依「使用者需求」表。bot 模式：用啟動參數切換，忽略玩家輸入，自動依序走向 3 枚金幣與終點。`git commit`。

## Phase 8：測試與畫面檢查

1. bot 測試通過
2. 物理測試通過：「移動」與「物理互動」兩列需求的每一項，都要有你訂的可量測門檻；門檻和理由寫進 log
3. 用 Godot MCP 執行遊戲，沒有錯誤
4. 取得遊戲畫面截圖：包含一般遊玩畫面，以及看得到整個地塊的畫面。依附錄 B 檢查，不合格就判斷是資產問題（回 Blender）還是場景問題（修 Godot），修完重拍
5. `git commit`

## Phase 9：迴圈演練

模擬「Godot 端發現資產需要修改」：
1. 在 log 寫下回饋：金幣太大、擋視線，規格改小（約原本的 60%）
2. 修改金幣規格，執行自動檢查 → 應該 FAIL（確認檢查機制有效），並記錄
3. 依修正建議回 Blender 調整 → 匯出 → 檢查 PASS
4. 同步調整遊戲端與金幣尺寸相關的設定；bot 測試與物理測試仍通過
5. 重新執行遊戲確認畫面，`git commit`

## Phase 10：收尾

1. 撰寫 `pipeline/REPORT.md`：DoD 勾選結果、每個資產的迭代次數、MCP 問題與替代做法、物理測試的門檻與實測數字、主要設計決策與理由、遇到的問題與解法、花最多時間的步驟、建議的下一步
2. `git commit`
3. 告訴使用者完成了，附 REPORT 摘要

## 附錄 A：資產目標

尺寸、面數、顏色、結構、命名都由你訂；比例要合理，風格要一致。

| 資產 | 要表達什麼 | 遊戲上的要求 |
|---|---|---|
| 機器人 | 可愛的單輪小機器人 | 輪子要能在遊戲中轉動，且看得出在轉 |
| 金幣 | 金幣 | 可以被收集 |
| 終點旗 | 旗桿加旗子 | 碰到就判定抵達終點 |
| 木箱 | 和場景風格搭配的木箱 | 擺放位置合理 |
| 木桶 | 木桶 | 可以被機器人推動 |
| 樹 | 低模的樹 | 被撞會搖晃、掉落葉；平常隨風擺動 |
| 草叢 | 一叢灌木 | 機器人可以穿過，穿過時會晃；平常隨風擺動 |
| 石頭 | 石頭 | — |
| 磚瓦牆 | 磚瓦牆 | 圍住整個地圖，角色出不去 |
| 房子 | 小屋 | — |
| 古代奇幻風格建築 | 數量與種類由你決定 | — |
| 雲 | 低模雲朵 | 在空中漂移 |
| 地面 | 整個箱庭地塊 | 見附錄 C |

哪些物件會擋住機器人、哪些可以穿過，依遊戲合理性決定（草叢必須可以穿過）。

## 附錄 B：畫面檢查清單

- 一般遊玩畫面：機器人清楚可辨；看得到周圍的場景；陰影柔和；有移軸景深的迷你模型感
- 整體畫面：整個地塊都在畫面內；構圖豐富、沒有大片空白；所有場景元素都看得到；雲在空中，地上看得到雲的影子
- 地面：草坪不單調、不假；道路清楚；看得出高低起伏
- 沒有倒立、躺平、懸空、陷進地面的物件；高大的物件不會擋住玩家常走的區域
- 木箱的造型與擺放和場景搭配

## 附錄 C：地面目標

- 箱庭地塊的樣子：地塊有厚度、側面看得到土層，像放在桌上的模型
- 地表稍微有高低起伏；機器人爬得上去，bot 不會卡住
- 建築、圍牆等物件底下要平，物件放上去不懸空、不陷入
- 草坪有自然的深淺變化，不是單一顏色，也不雜亂
- 有道路連接主要區域
- 加上能讓地面更真實的點綴（種類由你決定）

## 附錄 D：版面目標

- 分區清楚、構圖豐富，同時留有可以跑動的空間
- 鏡頭是斜上方等角視角，高大的物件不要擋住玩家常走的區域
- 木箱、木桶要擺在合理的地方
- bot 的路線（起點 → 3 枚金幣 → 終點）不能被擋住
- 物理測試用到的物件，周圍要有空間讓測試能進行
